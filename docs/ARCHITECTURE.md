# Marmix Flex Redesign v2 — Technical Architecture

**Статус:** технический source of truth для последующих небольших TASK. Только проектирование: этот документ не создаёт приложение, схему БД, интеграции или разрешение на production. Ветка разработки — redesign-v2; main не изменять без прямого разрешения.

**Источники:** [утверждённая дизайн-система](DESIGN_SYSTEM.md), [контентный аудит](CONTENT_AUDIT.md), [история направления](DESIGN_DIRECTIONS.md), [утверждённый visual prototype](../prototype/index.html). При визуальном расхождении действуют приоритеты из DESIGN_SYSTEM.md: прототип и его фактические стили выше раннего направления. Товары, цены и интерьерные сцены прототипа демонстрационные. Контентный аудит выявляет кандидатов и пробелы, но не удостоверяет ассортимент, стоимость и условия доставки.

## 1. Решение и пределы

| Слой | Выбор | Почему |
|---|---|---|
| Web | Next.js App Router + React + TypeScript, Node runtime | Индексируемые серверные страницы, metadata, изображения и один серверный endpoint заявки без отдельного API-сервиса. Точную стабильную версию фиксировать при создании приложения. |
| UI | CSS Modules для секций/компонентов, глобальные CSS custom properties для утверждённых токенов, локальные Prata/Manrope через next/font/local после проверки лицензий | Сохраняет реальные пропорции, брейкпоинты и характер Dark Gold Showroom. Не вводить Tailwind, theme engine или библиотеку готовых карточек. |
| Данные и авторизация | Supabase Postgres + Storage + Supabase Auth; @supabase/supabase-js и @supabase/ssr | Публичный каталог читается с publishable key под RLS; заявку создаёт отдельный server-only secret client; администраторы работают со своей Auth session под RLS. Покупателям аккаунты не нужны. @supabase/ssr нужен только для cookie session и её обновления в Next.js. |
| Управление магазином | Собственная Admin Panel в том же приложении | Ежедневное управление каталогом, медиа и заявками без выдачи владельцу постоянной работы в Supabase Studio. Studio остаётся техническим/резервным инструментом. |
| Хостинг | Vercel Preview для redesign-v2, production позже отдельным согласованным действием | Проверяемые изменения по ветке и раздельные окружения. |
| Поиск/формы/состояние | PostgreSQL поиск для малого каталога; стандартные формы и URLSearchParams; корзина в localStorage | Не нужны отдельный search service, form/store library и backend корзины. |

Новые зависимости добавлять по наблюдаемой потребности. Для текущих требований достаточно Next.js, React, TypeScript, @supabase/supabase-js и @supabase/ssr: последняя нужна именно для серверной cookie session администратора. Тестовые инструменты выбираются при реализации задач; не вводить отдельную CMS, ORM, Redux, поисковый сервис, анимационный runtime или платёжный SDK заранее.

### Данные и границы исполнения

- Server Components по умолчанию: страницы, layout, карточки, каталог, Product Detail, SEO, выборка и отображение данных. Не гидратировать всю страницу ради одной кнопки.
- Малые Client Components: мобильное меню, галерея товара при интерактивной смене кадра, количество/добавление, корзина, форма отправки и позднее адаптер аналитики. Поиск, сортировка и фильтры через GET и URL могут обойтись обычными HTML-формами и ссылками.
- Публичные серверные модули Supabase и secret client не импортируются клиентскими островками. Для входа и загрузки медиа админский browser client с publishable key и пользовательской session допустим: прямой доступ к БД/Storage всё равно ограничен RLS; secret key никогда не попадает в browser. Публичному посетителю не передаются записи заявок.
- Публичные запросы к БД идут из Next server с publishable key и RLS, без прямой клиентской подписки или Realtime. Варианты выборки скрыты за функциями getPublishedProduct, listPublishedProducts, getCatalogFacets; одна точка строит ограничения запроса.
- Admin pages и формы серверные; мелкие client islands для загрузки/preview фото, таблиц, подтверждения опасных действий и оперативной обратной связи. Админский SSR client передаёт пользовательский access token в Supabase и действует как authenticated под RLS; каждое чтение и изменение в Admin Panel повторно проверяет полномочия.
- Для повторного использования продукта между generateMetadata и страницей применять memoization одного server query в рамках запроса. Не дублировать запросы через собственный публичный API.

| /admin | Небольшой operational dashboard: счётчики new/in_progress заявок, опубликованных и неопубликованных товаров, ссылки на каталог и заявки. Без BI и публичного кеша. |
| /admin/products, /admin/products/new, /admin/products/[id] | Список/поиск/статус, создание и редактирование SKU, публикации, SEO и изображений; [id] — стабильный UUID, не изменяемый slug. |

| /admin/orders, /admin/orders/[id] | Список со статусным фильтром и сортировкой по дате; детальная заявка, изменение статуса и приватная заметка. [id] — UUID. |

Публичный layout объединяет Header, Footer, базовые метаданные и типографику. /admin/login без общего публичного showroom header; защищённый /admin layout — рабочая навигация, проверка доступа и собственные loading/error. Layout-guard нужен для UX, но каждое чтение/мутация проверяет доступ самостоятельно: Server Actions можно вызвать напрямую. Все /admin/* — noindex, force-dynamic и no-store, нельзя кэшировать HTML/ответ с session cookies. Страницы каталога используют общие CatalogHeader, FilterBar, ProductGrid; данные поступают из сервера. loading.tsx и error.tsx размещать у каталога/Product Detail по мере реализации, с короткими устойчивыми скелетами и предложением повторить запрос; not-found.tsx для удалённых товаров, спокойный fallback для ошибки заявки. Не размножать layout и error boundary без различий в поведении. Публичные фильтры и страницы каталога должны работать при выключенном JS; интерактивные покупки/корзина показывают честное состояние ожидания гидратации.

Компонентное деление по бизнес-взаимодействию: общий примитив только для повторяемого управления; Hero/Showcase не превращать в абстрактный конструктор страниц. AdminForm/ProductEditor/OrderStatus — отдельные feature-компоненты, общие с публичной частью только действительно повторяемые базовые controls и design tokens. Стили CSS Modules рядом с компонентом. Архитектура не предписывает менять prototype.

### Admin Auth: один тип доступа

- **Вход:** Supabase Auth email/password. В проекте отключить «Allow new users to sign up», anonymous sign-in и неиспользуемые провайдеры; в приложении нет sign-up. Первого и последующих администраторов создаёт владелец вручную через доверенный технический интерфейс Supabase Auth, после чего отдельно добавляет их UUID в закрытую таблицу admin_users. Само наличие Auth account, email domain или client metadata **не даёт** права admin. Без активной записи в admin_users вход в Admin Panel отклоняется, даже если удалось аутентифицироваться.
- **Определение admin:** admin_users(user_id → auth.users.id, is_active). Наличие активной строки означает единственную MVP роль admin. Таблицу нельзя менять из обычной пользовательской session: только владелец с техническим доступом вне Admin Panel создаёт/деактивирует администраторов. Нет публичной регистрации, самостоятельного приглашения или самоэскалации роли.
- **Session:** @supabase/ssr хранит и обновляет Auth session в cookies; proxy/middleware на /admin/* обновляет истекающий токен, но не служит единственной защитой. requireAdmin() на сервере обращается к Auth через getUser() (с проверкой актуальности session) и проверяет активную membership в admin_users с пользовательским JWT. Не основывать авторизацию на getSession() или пользовательских claims/данных client. При невалидной/истёкшей session — на /admin/login с безопасным локальным return path; при действующем аккаунте без admin допуска — отказ и signOut без раскрытия данных. Повторная авторизация не возобновляет несохранённую мутацию автоматически.
- **Права:** защищённый layout проверяет страницу; каждый Server Action/Route Handler и каждый запрос к приватным данным заново вызывает requireAdmin(). Для DB/Storage mutation используется cookie-based Supabase client с JWT пользователя, **не** secret client. RLS с проверкой admin_users повторяет то же решение в БД; прямое обращение к Supabase API с publishable key не обходит его. По завершении signOut() в серверном действии удаляет session cookies и переводит на /admin/login; дальнейшие запросы отклоняются. При деактивации membership следующий запрос отвергается даже при ещё действительном Auth token.
- **Login hygiene:** сильный пароль и подтверждённый email, штатные ограничения попыток Supabase Auth, HTTPS и настройка redirect URLs только для доверенных доменов. Позднее можно добавить MFA, если бизнес потребует, без смены модели данных. Admin Auth на Preview — отдельные тестовые аккаунты в отдельном проекте, production credentials не копировать в Preview.

## 3. Каталог: модель, поиск и фильтры

**Инвариант товара:** одна строка products соответствует одному конкретному продаваемому SKU и одной фиксированной единице цены. Если один декор продаётся в разных форматах с разной ценой, каждый формат — отдельный SKU с собственным slug; серия связывает их для отображения похожих товаров. Не смешивать цену за м² с количеством листов: количество в корзине всегда кратно указанной sale_unit и шагу продажи. Формат, площадь и реальные единицы необходимо подтвердить с бизнесом до импорта.

Категории редактируются как данные, а не код. Стартовое разделение «декоративные поверхности / сопутствующие материалы» из аудита — гипотеза до сверки фактического каталога. Не вводить фиктивные коллекции и скидочные статусы.

| Данные | Обязательное правило |
|---|---|
| Идентичность | UUID, уникальные slug и SKU, имя, category_id, необязательная серия. Slug стабильный; при переименовании старого URL нужен согласованный redirect. Физическое удаление товара по умолчанию запрещено: снять с публикации или пометить archived_at, сохранив SKU, slug и историю заявки. |
| Коммерция | price_minor — целые копейки RUB за sale_unit; sale_unit из короткого управляемого набора (например м²/лист/упаковка), quantity_step и min_quantity положительны. Цена или единица неизвестны — продукт нельзя заказать онлайн, показать запрос цены без фиктивной суммы. |
| Размер и свойства | width_mm, height_mm, thickness_mm и площадь/фасовка только если подтверждены. Технические характеристики в контролируемом specifications JSONB для показа; необязательные color_family, pattern и applications (контролируемый список) заполнять и индексировать под фильтры лишь при достаточном покрытии данных. |
| Статус | is_published, archived_at и availability_status (available/on_request/unavailable), необязательные featured и sort_order. «В наличии» не означает точный остаток без учёта складского источника. Архивный SKU нельзя снова публиковать до явного восстановления. |
| Связи | Категория, галерея, связанные товары по подтверждённой серии или категории без обязательной таблицы ручных связей. Для аксессуаров совместимость не объявлять автоматически. |

Каталог → валидированный URL (/catalog?q=…&category=…&sort=…&page=…) → один серверный запрос только к опубликованным данным → фасеты из реально заполненных атрибутов → карточка → товар → локальная корзина. Категория по slug — отдельный route; одинаковые параметры в обоих списках. Whitelist ключей/сортировок, ограничение длины q и page, лимит размера страницы. Поиск сначала по русскоязычным имени/SKU/серии и подтверждённому описанию средствами PostgreSQL; при малом каталоге достаточно простого поиска, полнотекстовый GIN индекс вводить с задачей поиска при наличии данных. Фильтры первоначально категория, цена и подтверждённый статус; цвет/рисунок/применение только после полноты атрибутов и понятных значений. Не добавлять универсальный движок фильтров по JSONB.

При снятии категории с публикации все её товары исчезают из публичного каталога и Product Detail по RLS, но их записи и собственные флаги публикации остаются. Admin UI показывает количество затронутых товаров и подтверждает действие; повторная публикация категории возвращает ранее опубликованные товары, поэтому требует предварительной проверки. Удаление категории с товарами запрещено; сначала переместить товары или оставить категорию неопубликованной. Смена slug категории или товара создаёт задачу на 301 redirect, а не молчаливое уничтожение входящих ссылок.

## 4. Медиа

Хранить утверждённые изображения в публичном бакете Supabase Storage по стабильным ключам; исходные черновики не считать публично приватными после загрузки в такой бакет. Публикация записи product_images — после проверки прав, точного соответствия SKU, alt и роли кадра. Роли: neutral_texture (основной товарный образец), macro, interior, application; отдельное самостоятельное «thumbnail» изображение не требуется — размеры выдаёт Next/Image. Отмечать «визуализация» отдельно от реального проекта.

Admin Panel показывает выбор файла/preview, alt, роль, порядок и primary без ручного ввода storage_path. Допускается прямой upload из admin browser в Storage **только** с пользовательской Auth session и publishable key под admin-only Storage RLS: бакет и префикс товаров фиксированы, путь генерируется интерфейсом, bucket ограничен разрешёнными типами и размером файла; метаданные product_images сохраняются отдельной защищённой мутацией. Ни upload, ни удаление не используют secret key. Для MVP медиа бакет публичный: даже файл неопубликованного товара при известном URL доступен, поэтому туда попадают только разрешённые к показу материалы; для конфиденциальных черновиков понадобится отдельный private bucket в будущей задаче.

Перестановка, primary, alt и роль управляются через Admin Panel; сервер проверяет принадлежность товара, допустимые роли, один primary и наличие актуального primary до публикации. Удаление сначала отвязывает изображение от карточки, затем удаляет Storage object; при ошибке удаления показывает предупреждение и позволяет повторить очистку оставшегося объекта, не оставляя битую публичную ссылку. Первичный или единственный кадр опубликованного товара не удалять, пока не назначена замена либо товар не снят с публикации. Не перезаписывать файл по прежнему URL при смене ракурса: новый ключ избегает устаревших CDN копий.

Таблица product_images хранит product_id, storage_path, role, alt, width, height, sort_order и флаг основного кадра с ограничением одного primary на товар. Хранить исходник высокого качества; готовить правдоподобные WebP/AVIF и цветовые профили. На товарной карточке нейтральный свет, не делать цвет фактуры янтарным ради темы. Интерьер может быть теплее, но не подменяет товарный образец.

Next/Image с точно ограниченным remotePatterns до бакета, заполненными размерами/контейнером и sizes для 1440/390 и промежуточных ширин. Уважать пропорции DESIGN_SYSTEM.md (карточка около 1.1 desktop / 1.23 mobile, крупная асимметричная пара showcase), менять кадрирование по точке фокуса и фактуре без деформации. LCP Hero: один реально видимый кадр приоритетной загрузки/preload, отдельный mobile crop при необходимости; остальные медиа lazy, без preload всех товарных карточек. Проверить скорость и артефакты оптимизатора на реальных фото.

## 5. Корзина и заявка

**До оформления:** версия корзины в localStorage браузера, записи product_id, quantity и необязательный snapshot name/image/price_minor/unit для немедленного UI. Snapshot не авторитетен для цены. Ключ версионирован; повреждённые/устаревшие данные сбрасываются безопасно, одинаковые ID объединяются, количество ограничено и кратно quantity_step. Гидратация не должна показывать неверный «пустой» итог как конечный результат; при первом открытии клиент сверяет список товаров с сервером через чтение каталога по допустимым ID, удалённые/недоступные позиции обозначает явно. Cart drawer необязателен; /cart — обязательный путь. Не создавать таблицу carts и пользовательскую сессию.

**Путь:** Product Detail → add_to_cart → /cart (количество/удаление/итог) → /checkout (контакты и подтверждение) → ответ сервера → состояние «Заявка отправлена», номер без персональных данных. Минимальные поля: имя, телефон, согласие с политикой; город/способ получения и комментарий — только если они нужны согласованному процессу продаж (иначе опциональны). Не собирать паспорт, адрес или платёжные реквизиты заранее. Форма показывает loading, success/error, предотвращает повторный клик и допускает повтор после сетевой ошибки.

POST /api/order-requests получает строки {product_id, quantity}, контактные поля, idempotency_key (случайный UUID, сохраняемый на клиенте при повторе одной заявки), версию и показанный price_minor каждого SKU. Сервер проверяет форму, согласие, максимальные размеры запроса/количество позиций/значения; для уже записанного ключа сначала сравнивает хеш нормализованного payload и безопасно возвращает прежний результат. Для новой заявки заново читает активные товары **без кеша**, проверяет шаг продажи и статус, рассчитывает цены и итог в целых копейках. Изменение цены, единицы или недоступность → 409 с безопасным объяснением и обновлённой суммой; пользователь подтверждает обновлённую корзину новой попыткой с новым ключом. Никакие клиентские суммы и поля товара не идут в запись без серверной сверки.

Заявка — **одна атомарная запись** order_requests со снимком проверенных строк items_snapshot JSONB, total_minor, currency, контактами, статусом, created_at, idempotency_key и request_hash. UNIQUE(idempotency_key) защищает от повторной записи при таймауте и двойном submit. Повтор с тем же ключом и тем же payload возвращает тот же безопасный номер, иной payload → конфликт без утечки содержимого чужой заявки; не сообщать PII в ответе. Это осознанно заменяет отдельную order_items: для заявки менеджеру пока не требуется отдельный учёт исполнения, а одна вставка не создаёт частично записанных заказов. Если появятся складское резервирование, частичная отгрузка или оплата по позициям, тогда потребуется транзакционная нормализация в отдельной архитектурной задаче.

Онлайн-оплаты нет. Когда она станет бизнес-требованием, добавить отдельный платёжный контур с серверной верификацией и связью с заявкой; не считать сумму из localStorage основанием для платежа.

## 6. Supabase: таблицы и доступ

| Сущность | Ключевые поля, связь, индекс | Доступ |
|---|---|---|
| categories | id, slug UNIQUE, title, description, sort_order, is_published, SEO поля; индекс публикация+порядок | anon SELECT опубликованных; authenticated active admin SELECT/INSERT/UPDATE. Удаление через UI не предусматривать. |
| products | id, category_id FK, slug UNIQUE, sku UNIQUE, name, series, описания/SEO, price_minor, currency, sale_unit, min_quantity/quantity_step, размеры, необязательные color_family/pattern/applications, controlled specifications JSONB, availability_status, is_published, archived_at, featured, sort_order; индекс category_id+is_published+sort_order, частичный индекс featured при необходимости | anon SELECT только опубликованных, неархивных, в опубликованной категории; authenticated active admin SELECT/INSERT/UPDATE, включая неопубликованные; физический DELETE не давать. |
| product_images | id, product_id FK, storage_path, role, alt, width/height, sort_order, is_primary; индекс product_id+sort_order, уникальность primary на product_id | anon SELECT только для опубликованного товара/категории; authenticated active admin SELECT/INSERT/UPDATE/DELETE; Storage DELETE с отдельной admin RLS policy. |
| order_requests | id UUID, created_at, updated_at, status (new/in_progress/completed/cancelled), internal_note nullable, name, phone, необязательные city/comment, consent_at, items_snapshot JSONB, total_minor, currency, idempotency_key UNIQUE, request_hash; индекс status+created_at для очереди | anon: никаких прав. authenticated active admin: SELECT и UPDATE **только** status/internal_note. INSERT только server-only secret client после проверки public POST; нет DELETE. updated_at поддерживается БД. |
| admin_users | user_id UUID PK → auth.users.id, is_active, created_at; индекс PK достаточен. Наличие активной строки = роль admin, без иных ролей/claims | anon: нет прав. authenticated: SELECT только своей строки по auth.uid(); INSERT/UPDATE/DELETE закрыты. Владелец управляет доступом через доверенный технический инструмент. |

**RLS обязательно** на всех прикладных таблицах. SQL GRANT отдельно ограничивает операции до проверки RLS. Для публичного SELECT категории/товара/изображения — только опубликованные связанные строки; для админских CRUD и чтения заявок — authenticated пользователь с активной записью admin_users. Membership policy самой admin_users — прямое сравнение user_id = auth.uid(), без рекурсивного обращения к этой таблице; обычный пользователь не может записать себя в администраторы. Отдельно проверить grants на всех новых таблицах Supabase: не полагаться на настройки default exposure проекта.

На order_requests **отозвать table-level UPDATE у authenticated**, выдать только column-level UPDATE(status, internal_note), проверить status по ограниченному списку и обновлять updated_at триггером БД. Тогда даже authenticated admin с прямым доступом к Data API не сможет изменить телефон, позиции, цену, итог, время создания, request_hash или idempotency_key: исходный commercial snapshot остаётся неизменным. Серверное действие ограничивает допустимые переходы статуса и размеры внутренней заметки; обход action через Supabase API всё равно не меняет исходные коммерческие поля. updated_by пока не вводить: источник прав — текущая membership, а надёжная история изменений потребует отдельного требования аудита.

Только публичный POST создаёт заявку с server-only secret key. Этот ключ действует как service_role и обходит RLS, поэтому не использовать его для обычных Admin CRUD/чтения и никогда не помещать в browser, NEXT_PUBLIC_*, логи или Git. Ответ публичного POST содержит лишь безопасный номер; internal_note не включается ни в DTO заказа, ни в публичные endpoints. Для Storage отдельно разрешить active admin INSERT/SELECT/DELETE в пределах product media bucket/префикса; публичная доставка файлов бакета не делает доступными таблицу заявок или Storage mutations. Supabase Auth покупателям не требуется.

**Порядок будущей реализации:** маленькая задача на схему, grants/RLS и негативные проверки anon/authenticated; далее закрытый Auth и guard, Admin Catalog, Storage, заявки, затем публичный каталог/покупка по зависимостям. Здесь нет SQL и migrations.

## 7. Admin Panel как рабочий интерфейс

**Выбор:** собственная Admin Panel — основной operational interface. Supabase Dashboard/Studio — только технический резерв для создания admin account, восстановления и обслуживания БД. Не строить визуальный page builder, общую CMS или многоуровневый RBAC. По сравнению со Studio это ограничивает повседневные действия ровно каталогом и заявками; по сравнению с внешней CMS не дублирует БД и модель ролей.

**Dashboard:** четыре небольших показателя: новые заявки, заявки в работе, опубликованные товары, снятые с публикации/архивные товары (последние показывать раздельно, если учитываются оба). Быстрые переходы в /admin/products и /admin/orders. Счётчики — текущие серверные выборки под Admin RLS, не отдельная BI схема.

**Product editor:** поля name, slug, SKU, category, series, description, price_minor и единица продажи, min_quantity, quantity_step, размеры, specifications, контролируемые color_family/pattern/applications при их наличии, availability, is_published, archived_at, featured, sort_order, SEO title/description и галерея. Создание, редактирование, снятие/возврат публикации, архивирование; редактирование slug требует предупреждения и redirect-плана. Публикация допускается только с проверенными обязательными коммерческими данными и основным товарным фото, если фото обязательно для публичной карточки. Редактор видит сохранение/ошибку и явное состояние «опубликован». Физическое удаление товара не предусматривается в MVP.

**Category editor:** title, slug, description, sort_order, is_published, SEO. Перед снятием с публикации показывать число опубликованных товаров; скрывать категорию целиком без изменения дочерних записей, предупреждать перед повторной публикацией. Нельзя удалять категорию с товарами, нельзя скрыто менять публичные URL без redirect-плана.

**Orders:** список номера/даты/статуса/имени/телефона с фильтром по статусу и сортировкой по дате; detail показывает товары, quantity, sale unit, зафиксированные цену/итог и необязательный комментарий клиента. Редактируются только status и internal_note, остальные поля read-only, без кнопок для изменения коммерческого снимка. Переход статуса подтверждается на сервере; заметка не попадает в публичный ответ или аналитику. Без сложной истории действий, CRM или встроенной оплаты в MVP.

**Админский visual language:** graphite/dark foundation, Manrope для UI, аккуратный gold только на активном действии, прямые читаемые таблицы и формы, высокий контраст, понятные предупреждения и почти нет декоративного motion. Prata — лишь редкие заголовки без ущерба плотности. Приоритет clarity → speed → safety → brand consistency; утверждённый публичный Dark Gold Showroom не копировать в рабочие таблицы и не изменять.

**Responsive:** desktop — продуктивные таблицы и редактор с видимыми действиями; tablet — укрупнённые рабочие области и сокращённые колонки; phone — строки заявок/товаров в компактных вертикальных группах, формы в один столбец и доступные действия публикации/статуса/медиа. Горизонтальный скролл таблицы только локальный с видимыми ключевыми полями; основные действия доступны без hover. Не проектировать phone как уменьшенный desktop и не жертвовать desktop плотностью ради mobile.

## 8. SEO и аналитика

Metadata API: шаблон title и description для статичных маршрутов, generateMetadata для опубликованных категорий и товаров, один production SITE_URL для абсолютных canonical. 404/noindex для неопубликованного, /cart и /checkout исключены из индекса; страницы поиска/фильтров canonical на базовый каталог/категорию, без индексации комбинаций. Все /admin/*, включая login, — noindex, отсутствуют в sitemap; robots исключает /admin, но robots/noindex не являются защитой доступа. app/sitemap.ts только canonical опубликованных URL; app/robots.ts исключает служебные маршруты, Preview целиком noindex и без production sitemap. Open Graph использует разрешённые реальные изображения. JSON-LD BreadcrumbList для вложенности, Product/Offer — только при подтверждённых цене, RUB, единице и корректном наличии; не выдумывать ratings, reviews или сроки доставки. Региональный текст про Сургут и коммерческие условия только после проверки CONTENT_AUDIT.md.

Архитектура будущей Яндекс Метрики: маленький клиентский адаптер за флагом production, один набор имён целей: catalog_view, product_view, add_to_cart, remove_from_cart, begin_checkout, order_submit, contact_click, phone_click. Вызов reachGoal после фактического действия; order_submit только после серверного success и один раз на idempotency_key. При App Router переходах pageview обрабатывать отдельно, без двойного учёта. Не отправлять имя, телефон, комментарий, ID заявки и произвольный текст поиска. Текущий этап ничего не подключает; правила согласия и текст политики уточняются перед запуском.

## 9. Производительность, безопасность, развёртывание

- **Сервер и cache:** RSC для публичного контента, нулевой клиентский JS у статичных информационных страниц. Публичный каталог кешировать явно по понятному TTL; после Admin save/publish/price/status делать адресную revalidation затронутого товара/категории/списка, а TTL оставить запасным сроком свежести. Админские страницы и приватные данные никогда не входят в общий cache/CDN, ответы с Set-Cookie не кешировать. Цены и доступность при публичном POST всегда читать свежими, независимо от cache каталога. Не полагаться на неявные дефолты конкретной версии Next.
- **Клиент и motion:** динамически загружать только действительно интерактивную галерею/корзину там, где она используется; картинки ниже первого экрана лениво. Отложенная Метрика, шрифты локально с оптимальным subset и font-display swap. Анимации через opacity/transform, утверждённые длительности и prefers-reduced-motion; никаких тяжёлых parallax библиотек. Проверять LCP/CLS и полезность больших кадров на 1440 и 390.
- **Граница ввода:** runtime validation на сервере, whitelist ключей и длины, нормализация телефона без потери исходной пригодности для менеджера, ограничения строк/количества; React экранирует обычные строки, не рендерить произвольный HTML из БД. Admin mutations: requireAdmin при каждом вызове, только разрешённые поля, уникальность slug/SKU и ограничения БД, проверки шага/цены/категории и безопасные сообщения об ошибке. У публичного POST проверять допустимый Origin, Content-Type и размер тела; не считать Origin единственной защитой от скриптов. Для админских Server Actions оставить same-origin CSRF protection Next, не расширять allowedOrigins без нужды, а для отдельного upload/logout Route Handler явно проверять Origin, session и HTTP method; auth cookies с Secure/SameSite в production. Honeypot + ограничения потока по факту злоупотреблений; при необходимости Vercel WAF/общий rate limiting, а не Map в памяти serverless.
- **Секреты и логи:** все реальные значения — только Vercel env/local untracked env, никогда в Git. Публичный publishable key и URL могут быть в admin browser; secret key — только в серверном endpoint записи заявки. Логировать код ошибки, случайный correlation ID и время, но не контакты, содержимое заказа/заметки, session cookies, токены и payload. Доступы к Supabase/Vercel выдать по минимальным полномочиям; хранение PII, основания обработки и место размещения данных проверить отдельно до production.
- **Окружения:** GitHub redesign-v2 → автоматический Vercel Preview с отдельными переменными и неиндексируемым URL → QA → production лишь по отдельному разрешению и согласованному способу promotion. main не затрагивать автоматически. Preview связан только с отдельным тестовым Supabase проектом и тестовыми admin users; разрешённые Auth redirect URLs соответствуют доменам окружения. Production использует отдельные Auth users, Storage и БД. Проверять отсутствие кеширования админских страниц и ответов с Set-Cookie на Vercel. Supabase production project создавать на последующем этапе, не сейчас.

| Будущая переменная | Где | Назначение |
|---|---|---|
| NEXT_PUBLIC_SUPABASE_URL | browser и server | URL проекта данных; отдельно Preview/Production, не секрет. |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | browser и server | Публичное чтение + Auth/Storage admin с JWT под RLS; не предоставляет доступ к заявкам без роли. |
| SUPABASE_SECRET_KEY | server-only env | Привилегированная запись заявки; новая secret key вместо legacy service_role JWT. Не передавать в клиент. |

| YANDEX_METRIKA_ID | server env, передаётся только в разрешённый production адаптер | Идентификатор счётчика, не секрет; подключение позже. |

В Vercel дополнительно доступен VERCEL_ENV для различия Preview/Production. Сами значения и .env не коммитить; если потребуется .env.example, только безопасные placeholders. Проверять, что Preview не содержит метрики production и не отправляет реальные заявки. У public read client не должно быть пользовательских admin cookies: бизнес-правило публикации остаётся одинаковым для гостя и администратора при просмотре публичной витрины.

## 10. Reusable legacy candidates

Старый проект — источник для точечной проверки: тексты о бизнесе, права на настоящие фотографии/проекты, выгрузка SKU и атрибутов, условия доставки и контакты, полезные правила расчёта количества и единицы продажи, существующие URL для плана redirect. Каждый кандидат отдельно проверяется на актуальность, права, безопасность, соответствие архитектуре и утверждённому visual language. Старый код/разметку целиком не переносить.

| Проверка | Результат |
|---|---|
| Простота | Одно Next-приложение, один Supabase project на окружение, Admin Panel в том же приложении; нет отдельной CMS, backend корзины, платёжной или BI системы. |

| Гости | anon не читает заявки и не меняет товары, категории, изображения или Storage. Публичный submit имеет один контролируемый server-only endpoint. |
| Admin mutations | requireAdmin на сервере при каждом чтении/действии; DB и Storage RLS проверяют активный admin независимо от UI. Только запись публичной заявки использует secret key, browser — никогда. |
| Исходная заявка | authenticated получает лишь column UPDATE(status, internal_note); товары, цена, итог и контактные поля снимка неизменяемы даже через прямой Data API. |
| Приватность | internal_note доступна только admin и отсутствует в публичном DTO, sitemap, клиентской аналитике и логах. Admin routes не кешируются. |
| Независимые TASK | Отдельные будущие задачи: схема/RLS+негативные проверки, Auth+guard, admin dashboard, категории, редактор товара, Storage, заявки/статусы, затем публичная витрина/checkout и QA. Это не TASKS.md и не разрешение начать реализацию. |

**Перед реализацией коммерции подтвердить:** полный ассортимент и SKU, единицы продажи и шаг, действующие цены/наличие, свойства/применение, доставка/оплата/возврат, реальные контакты, лицензии медиа и текст согласия. Если появятся требование мгновенного учёта остатков, варианты с общей ценой, обязательная онлайн-оплата или дополнительные роли сотрудников — сначала пересмотреть соответствующую часть архитектуры, затем реализовывать.
