# Marmix Flex Redesign v2 — Technical Architecture

**Статус:** технический source of truth для последующих небольших TASK. Только проектирование: этот документ не создаёт приложение, схему БД, интеграции или разрешение на production. Ветка разработки — redesign-v2; main не изменять без прямого разрешения.

**Источники:** [утверждённая дизайн-система](DESIGN_SYSTEM.md), [контентный аудит](CONTENT_AUDIT.md), [история направления](DESIGN_DIRECTIONS.md), [утверждённый visual prototype](../prototype/index.html). При визуальном расхождении действуют приоритеты из DESIGN_SYSTEM.md: прототип и его фактические стили выше раннего направления. Товары, цены и интерьерные сцены прототипа демонстрационные. Контентный аудит выявляет кандидатов и пробелы, но не удостоверяет ассортимент, стоимость и условия доставки.

## 1. Решение и пределы

| Слой | Выбор | Почему |
|---|---|---|
| Web | Next.js App Router + React + TypeScript, Node runtime | Индексируемые серверные страницы, metadata, изображения и один серверный endpoint заявки без отдельного API-сервиса. Точную стабильную версию фиксировать при создании приложения. |
| UI | CSS Modules для секций/компонентов, глобальные CSS custom properties для утверждённых токенов, локальные Prata/Manrope через next/font/local после проверки лицензий | Сохраняет реальные пропорции, брейкпоинты и характер Dark Gold Showroom. Не вводить Tailwind, theme engine или библиотеку готовых карточек. |
| Данные | Supabase Postgres + Storage; @supabase/supabase-js в server-only модулях | Одна управляемая база и хранилище медиа. Публичный каталог читается с publishable key под RLS; запись заявки — отдельным привилегированным серверным клиентом. Auth покупателям не нужен. |
| Хостинг | Vercel Preview для redesign-v2, production позже отдельным согласованным действием | Проверяемые изменения по ветке и раздельные окружения. |
| Поиск/формы/состояние | PostgreSQL поиск для малого каталога; стандартные формы и URLSearchParams; корзина в localStorage | Не нужны отдельный search service, form/store library и backend корзины. |

Новые зависимости добавлять по наблюдаемой потребности. На старте достаточно Next.js, React, TypeScript и @supabase/supabase-js. Тестовые инструменты выбираются при реализации задач; не вводить CMS, ORM, Redux, поисковый сервис, анимационный runtime или платёжный SDK заранее.

~~~mermaid
flowchart TD
    A["Browser: страницы и локальная корзина"] --> B["Next.js: RSC и клиентские островки"]
    B --> C["Supabase: опубликованный каталог / Storage"]
    A --> D["POST /api/order-requests"]
    D --> E["Проверка данных и актуальных цен"]
    E --> F["Supabase: одна приватная запись заявки"]
    G["Supabase Dashboard: ограниченный доступ редактора"] --> C
    G --> F
~~~

### Данные и границы исполнения

- Server Components по умолчанию: страницы, layout, карточки, каталог, Product Detail, SEO, выборка и отображение данных. Не гидратировать всю страницу ради одной кнопки.
- Малые Client Components: мобильное меню, галерея товара при интерактивной смене кадра, количество/добавление, корзина, форма отправки и позднее адаптер аналитики. Поиск, сортировка и фильтры через GET и URL могут обойтись обычными HTML-формами и ссылками.
- Серверные модули Supabase не импортируются клиентскими островками. Клиенту передаются только безопасные данные товара; доступ к таблице заявок нигде в браузере не открыт.
- Публичные запросы к БД идут из Next server с publishable key и RLS, без прямой клиентской подписки или Realtime. Варианты выборки скрыты за функциями getPublishedProduct, listPublishedProducts, getCatalogFacets; одна точка строит ограничения запроса.
- Для повторного использования продукта между generateMetadata и страницей применять memoization одного server query в рамках запроса. Не дублировать запросы через собственный публичный API.

## 2. Маршруты и интерфейсные границы

| Маршрут | Назначение / решение |
|---|---|
| / | Утверждённый showroom как визуальная основа; реальные товары и доказуемые обещания только после сверки контента. |
| /catalog | Все опубликованные товары, поиск, фильтры, сортировка и пагинация в URL. |
| /catalog/[category] | Одна плоская категория по уникальному slug; 404 для неактивной/несуществующей. Не вводить вложенную иерархию без данных. |
| /product/[slug] | Один продаваемый SKU, медиа, цена с единицей, параметры, покупка и близкие товары. Неопубликованное — 404. |
| /applications | Подтверждённые сценарии применения; реализованные проекты добавлять только после верификации и получения прав. |
| /about, /delivery, /contacts | Компания, условия доставки/оплаты/возврата, актуальные контакты; FAQ сначала разделы на соответствующих страницах, без пустой самостоятельной страницы. |
| /cart | Полная доступная корзина с изменением количества, удалением и пустым состоянием. Небольшой drawer может быть дополнительным входом, страница остаётся основным рабочим маршрутом. |
| /checkout | Отдельная простая форма заявки, сумма и согласие; после успешного ответа — подтверждение в состоянии страницы с номером заявки. Онлайн-оплата и отдельный личный кабинет не предполагаются. |
| /privacy, /terms | Политика обработки персональных данных; условия продажи/заявки только после утверждения коммерческих формулировок. Ссылка на условия возврата находится в /delivery. |
| POST /api/order-requests | Единственный публичный endpoint мутации: валидация, повторная проверка каталога и цены, запись заявки. Остальных публичных API до необходимости нет. |

Layout приложения объединяет Header, Footer, базовые метаданные и типографику. Страницы каталога используют общие CatalogHeader, FilterBar, ProductGrid; данные поступают из сервера. loading.tsx и error.tsx размещать у каталога/Product Detail по мере реализации, с короткими устойчивыми скелетами и предложением повторить запрос; not-found.tsx для удалённых товаров, спокойный fallback для ошибки заявки. Не размножать layout и error boundary без различий в поведении. Публичные фильтры и страницы каталога должны работать при выключенном JS; интерактивные покупки/корзина показывают честное состояние ожидания гидратации.

Стили CSS Modules рядом с компонентом, одни утверждённые цвета/типографика/ритм в tokens.css. Архитектура не предписывает менять prototype.

## 3. Каталог: модель, поиск и фильтры

**Инвариант товара:** одна строка products соответствует одному конкретному продаваемому SKU и одной фиксированной единице цены. Если один декор продаётся в разных форматах с разной ценой, каждый формат — отдельный SKU с собственным slug; серия связывает их для отображения похожих товаров. Не смешивать цену за м² с количеством листов: количество в корзине всегда кратно указанной sale_unit и шагу продажи. Формат, площадь и реальные единицы необходимо подтвердить с бизнесом до импорта.

Категории редактируются как данные, а не код. Стартовое разделение «декоративные поверхности / сопутствующие материалы» из аудита — гипотеза до сверки фактического каталога. Не вводить фиктивные коллекции и скидочные статусы.

| Данные | Обязательное правило |
|---|---|
| Идентичность | UUID, уникальные slug и SKU, имя, category_id, необязательная серия. Slug стабильный; при переименовании старого URL нужен согласованный redirect. |
| Коммерция | price_minor — целые копейки RUB за sale_unit; sale_unit из короткого управляемого набора (например м²/лист/упаковка), quantity_step и min_quantity положительны. Цена или единица неизвестны — продукт нельзя заказать онлайн, показать запрос цены без фиктивной суммы. |
| Размер и свойства | width_mm, height_mm, thickness_mm и площадь/фасовка только если подтверждены. Технические характеристики в контролируемом specifications JSONB для показа; необязательные color_family, pattern и applications (контролируемый список) заполнять и индексировать под фильтры лишь при достаточном покрытии данных. |
| Статус | is_published и availability_status (available/on_request/unavailable), необязательные featured и sort_order. «В наличии» не означает точный остаток без учёта складского источника. |
| Связи | Категория, галерея, связанные товары по подтверждённой серии или категории без обязательной таблицы ручных связей. Для аксессуаров совместимость не объявлять автоматически. |

Каталог → валидированный URL (/catalog?q=…&category=…&sort=…&page=…) → один серверный запрос только к опубликованным данным → фасеты из реально заполненных атрибутов → карточка → товар → локальная корзина. Категория по slug — отдельный route; одинаковые параметры в обоих списках. Whitelist ключей/сортировок, ограничение длины q и page, лимит размера страницы. Поиск сначала по русскоязычным имени/SKU/серии и подтверждённому описанию средствами PostgreSQL; при малом каталоге достаточно простого поиска, полнотекстовый GIN индекс вводить с задачей поиска при наличии данных. Фильтры первоначально категория, цена и подтверждённый статус; цвет/рисунок/применение только после полноты атрибутов и понятных значений. Не добавлять универсальный движок фильтров по JSONB.

## 4. Медиа

Хранить утверждённые изображения в публичном бакете Supabase Storage по стабильным ключам; исходные черновики не считать публично приватными после загрузки в такой бакет. Публикация записи product_images — после проверки прав, точного соответствия SKU, alt и роли кадра. Роли: neutral_texture (основной товарный образец), macro, interior, application; отдельное самостоятельное «thumbnail» изображение не требуется — размеры выдаёт Next/Image. Отмечать «визуализация» отдельно от реального проекта.

Таблица product_images хранит product_id, storage_path, role, alt, width, height, sort_order и флаг основного кадра с ограничением одного primary на товар. Хранить исходник высокого качества; готовить правдоподобные WebP/AVIF и цветовые профили. На товарной карточке нейтральный свет, не делать цвет фактуры янтарным ради темы. Интерьер может быть теплее, но не подменяет товарный образец.

Next/Image с точно ограниченным remotePatterns до бакета, заполненными размерами/контейнером и sizes для 1440/390 и промежуточных ширин. Уважать пропорции DESIGN_SYSTEM.md (карточка около 1.1 desktop / 1.23 mobile, крупная асимметричная пара showcase), менять кадрирование по точке фокуса и фактуре без деформации. LCP Hero: один реально видимый кадр приоритетной загрузки/preload, отдельный mobile crop при необходимости; остальные медиа lazy, без preload всех товарных карточек. Проверить скорость и артефакты оптимизатора на реальных фото.

## 5. Корзина и заявка

**До оформления:** версия корзины в localStorage браузера, записи product_id, quantity и необязательный snapshot name/image/price_minor/unit для немедленного UI. Snapshot не авторитетен для цены. Ключ версионирован; повреждённые/устаревшие данные сбрасываются безопасно, одинаковые ID объединяются, количество ограничено и кратно quantity_step. Гидратация не должна показывать неверный «пустой» итог как конечный результат; при первом открытии клиент сверяет список товаров с сервером через чтение каталога по допустимым ID, удалённые/недоступные позиции обозначает явно. Cart drawer необязателен; /cart — обязательный путь. Не создавать таблицу carts и пользовательскую сессию.

**Путь:** Product Detail → add_to_cart → /cart (количество/удаление/итог) → /checkout (контакты и подтверждение) → ответ сервера → состояние «Заявка отправлена», номер без персональных данных. Минимальные поля: имя, телефон, согласие с политикой; город/способ получения и комментарий — только если они нужны согласованному процессу продаж (иначе опциональны). Не собирать паспорт, адрес или платёжные реквизиты заранее. Форма показывает loading, success/error, предотвращает повторный клик и допускает повтор после сетевой ошибки.

POST /api/order-requests получает строки {product_id, quantity}, контактные поля, idempotency_key (случайный UUID, сохраняемый на клиенте при повторе одной заявки), версию и показанный price_minor каждого SKU. Сервер проверяет форму, согласие, максимальные размеры запроса/количество позиций/значения; для уже записанного ключа сначала сравнивает хеш нормализованного payload и безопасно возвращает прежний результат. Для новой заявки заново читает активные товары **без кеша**, проверяет шаг продажи и статус, рассчитывает цены и итог в целых копейках. Изменение цены, единицы или недоступность → 409 с безопасным объяснением и обновлённой суммой; пользователь подтверждает обновлённую корзину новой попыткой с новым ключом. Никакие клиентские суммы и поля товара не идут в запись без серверной сверки.

Заявка — **одна атомарная запись** order_requests со снимком проверенных строк items_snapshot JSONB, total_minor, currency, контактами, статусом, created_at, idempotency_key и request_hash. UNIQUE(idempotency_key) защищает от повторной записи при таймауте и двойном submit. Повтор с тем же ключом и тем же payload возвращает тот же безопасный номер, иной payload → конфликт без утечки содержимого чужой заявки; не сообщать PII в ответе. Это осознанно заменяет отдельную order_items: для заявки менеджеру пока не требуется отдельный учёт исполнения, а одна вставка не создаёт частично записанных заказов. Если появятся складское резервирование, частичная отгрузка или оплата по позициям, тогда потребуется транзакционная нормализация в отдельной архитектурной задаче.

Онлайн-оплаты нет. Когда она станет бизнес-требованием, добавить отдельный платёжный контур с серверной верификацией и связью с заявкой; не считать сумму из localStorage основанием для платежа.

## 6. Supabase: таблицы и доступ

| Сущность | Ключевые поля, связь, индекс | Доступ |
|---|---|---|
| categories | id, slug UNIQUE, title, description, sort_order, is_published, SEO поля; индекс публикация+порядок | anon SELECT только опубликованных; запись только через Studio/привилегированный процесс. |
| products | id, category_id FK, slug UNIQUE, sku UNIQUE, name, series, описания/SEO, price_minor, currency, sale_unit, min_quantity/quantity_step, размеры, необязательные color_family/pattern/applications, controlled specifications JSONB, availability_status, is_published, featured, sort_order; индекс category_id+is_published+sort_order, частичный индекс featured при необходимости | anon SELECT только опубликованных в опубликованной категории; никаких INSERT/UPDATE/DELETE. |
| product_images | id, product_id FK, storage_path, role, alt, width/height, sort_order, is_primary; индекс product_id+sort_order, уникальность primary на product_id | anon SELECT только у опубликованного товара/категории; запись закрыта. Публичный Storage URL сам по себе не является приватным. |
| order_requests | id UUID, created_at, status, name, phone, необязательные city/comment, consent_at, items_snapshot JSONB, total_minor, currency, idempotency_key UNIQUE, request_hash; индекс status+created_at для обработки | Ни SELECT, ни INSERT, ни UPDATE, ни DELETE для anon/authenticated; только server-only secret client и доступ ответственных сотрудников в Studio. |

**RLS обязательно** для всех таблиц; SQL GRANT отдельно ограничивает достижимость объектов через Data API. На catalogue-таблицы выдать anon только SELECT и политики на опубликованные строки; на orders отозвать публичные права и не создавать публичных политик. Secret key использует роль service_role с bypass RLS — поэтому он допустим только в server-only модуле обработки заявки после полной валидации, никогда в browser, NEXT_PUBLIC_*, логах или Git. Для чтения использовать publishable key, даже на сервере, чтобы не обходить публикационные политики. Для Storage разрешено публичное получение только утверждённого media bucket; запись доступна административным ролям. Supabase Auth покупателю не требуется, anonymous customer не получает права на заявки, даже свои: ответ выдаётся только текущему POST. Никаких привилегированных SQL functions, открытых views и DB hooks пока не нужно.

**Согласованный порядок будущей реализации:** отдельная небольшая задача для схемы/RLS и проверок публичных запросов; отдельная для безопасного управления контентом; затем серверные чтения и заявка. Здесь SQL и migrations не создаются.

## 7. Управление контентом

| Подход | Оценка |
|---|---|
| Supabase Dashboard/Studio + Storage | Выбран для начала: небольшой ассортимент и редактирование ограниченным кругом доверенных сотрудников, без второй модели данных и интерфейса. Проверки обязательных полей, цены/единицы, публикации и изображения фиксируются в процедуре загрузки и ограничениях БД. Права доступа к проекту выдавать только уполномоченным; Studio предоставляет широкие полномочия. |
| Файлы/таблица вручную → импорт | Разумно как разовая подготовка/сверка; постоянный прайс вне БД быстро расходится с витриной. |
| Отдельная CMS или custom admin | Понадобится только если редакторам нужны ограниченные роли, workflow публикации или частое массовое редактирование. Не разрабатывать до подтверждённой нужды. |

Владелец обновляет цены, категории, статусы, фотографии и статусы заявок через Dashboard. Нужны проверка изменений и резервная копия перед массовым импортом; чувствительные контакты заявок доступны только ответственным. Операционные требования хранения/удаления персональных данных согласовать до production.

## 8. SEO и аналитика

Metadata API: шаблон title и description для статичных маршрутов, generateMetadata для опубликованных категорий и товаров, один production SITE_URL для абсолютных canonical. 404/noindex для неопубликованного, /cart и /checkout исключены из индекса; страницы поиска/фильтров canonical на базовый каталог/категорию, без индексации комбинаций. app/sitemap.ts только canonical опубликованных URL; app/robots.ts исключает служебные маршруты, Preview целиком noindex и без production sitemap. Open Graph использует разрешённые реальные изображения. JSON-LD BreadcrumbList для вложенности, Product/Offer — только при подтверждённых цене, RUB, единице и корректном наличии; не выдумывать ratings, reviews или сроки доставки. Региональный текст про Сургут и коммерческие условия только после проверки CONTENT_AUDIT.md.

Архитектура будущей Яндекс Метрики: маленький клиентский адаптер за флагом production, один набор имён целей: catalog_view, product_view, add_to_cart, remove_from_cart, begin_checkout, order_submit, contact_click, phone_click. Вызов reachGoal после фактического действия; order_submit только после серверного success и один раз на idempotency_key. При App Router переходах pageview обрабатывать отдельно, без двойного учёта. Не отправлять имя, телефон, комментарий, ID заявки и произвольный текст поиска. Текущий этап ничего не подключает; правила согласия и текст политики уточняются перед запуском.

## 9. Производительность, безопасность, развёртывание

- **Сервер и cache:** RSC для контента, нулевой клиентский JS у статичных информационных страниц. Статичные материалы кешируются по понятному TTL или с управляемой инвалидацией после публикации; пока Dashboard не вызывает webhook, использовать ограниченный TTL и документировать задержку обновления. Цены и доступность при POST всегда читать свежими, независимо от cache каталога. Не полагаться на неявные дефолты конкретной версии Next.
- **Клиент и motion:** динамически загружать только действительно интерактивную галерею/корзину там, где она используется; картинки ниже первого экрана лениво. Отложенная Метрика, шрифты локально с оптимальным subset и font-display swap. Анимации через opacity/transform, утверждённые длительности и prefers-reduced-motion; никаких тяжёлых parallax библиотек. Проверять LCP/CLS и полезность больших кадров на 1440 и 390.
- **Граница ввода:** runtime validation на сервере, whitelist ключей и длины, нормализация телефона без потери исходной пригодности для менеджера, ограничения строк/количества; React экранирует обычные строки, не рендерить произвольный HTML из БД. У публичного POST проверять допустимый Origin, Content-Type и размер тела; не считать Origin единственной защитой от скриптов. Honeypot + ограничения потока по факту злоупотреблений; при необходимости Vercel WAF/общий rate limiting, а не Map в памяти serverless.
- **Секреты и логи:** все реальные значения — только Vercel env/local untracked env, никогда в Git. Логировать код ошибки, случайный correlation ID и время, но не контакты/ключи/payload. Доступы к Supabase/Vercel выдать по минимальным полномочиям; хранение PII, основания обработки и место размещения данных проверить отдельно до production.
- **Окружения:** GitHub redesign-v2 → автоматический Vercel Preview с отдельными переменными и неиндексируемым URL → QA → production лишь по отдельному разрешению и согласованному способу promotion. main не затрагивать автоматически. Preview с реальными заявками должен обращаться к отдельному тестовому Supabase окружению; не направлять QA-заявки в production. Supabase production project создавать на последующем этапе, не сейчас.

| Будущая переменная | Где | Назначение |
|---|---|---|
| SUPABASE_URL | server env | URL проекта данных; отдельно Preview/Production. |
| SUPABASE_PUBLISHABLE_KEY | server env | Чтение опубликованных каталожных данных с RLS; публичный по природе, но не нужен в browser bundle. |
| SUPABASE_SECRET_KEY | server-only env | Привилегированная запись заявки; новая secret key вместо legacy service_role JWT. Не передавать в клиент. |
| SITE_URL | server env | Абсолютные canonical, sitemap и OG для конкретного окружения. |
| YANDEX_METRIKA_ID | server env, передаётся только в разрешённый production адаптер | Идентификатор счётчика, не секрет; подключение позже. |

В Vercel дополнительно доступен VERCEL_ENV для различия Preview/Production. Сами значения и .env не коммитить; если потребуется .env.example, только безопасные placeholders. Проверять, что Preview не содержит метрики production и не отправляет реальные заявки.

## 10. Reusable legacy candidates

Старый проект — источник для точечной проверки: тексты о бизнесе, права на настоящие фотографии/проекты, выгрузка SKU и атрибутов, условия доставки и контакты, полезные правила расчёта количества и единицы продажи, существующие URL для плана redirect. Каждый кандидат отдельно проверяется на актуальность, права, безопасность, соответствие архитектуре и утверждённому visual language. Старый код/разметку целиком не переносить.

## 11. Architecture self-review и точки следующего решения

| Проверка | Результат |
|---|---|
| Простота | Один Next-приложение, один Supabase project на окружение, один API endpoint; нет backend корзины, CMS, ORM, платежей и order_items без процесса исполнения. |
| Дизайн | CSS Modules и tokens сохраняют Prata/Manrope, пропорции 1800px shell, цвет/золото, mobile-композицию и фото из DESIGN_SYSTEM; prototype не изменён. |
| Компоненты и JS | Серверные страницы и обычные GET фильтры; клиент только для действующих взаимодействий. Общие компоненты лишь при повторении. |
| Безопасность | Публичный read под RLS; заявки без anon доступа; secret key в одном server-only модуле; повторная проверка цены и идемпотентность. |
| Независимые TASK | Можно отдельно сделать scaffold, медиа/контент, схему/RLS, read catalog, product, cart, request flow, информационные страницы, SEO, analytics, Preview/QA. Это последовательность зависимостей, не TASKS.md и не разрешение начать. |

**Перед реализацией коммерции подтвердить:** полный ассортимент и SKU, единицы продажи и шаг, действующие цены/наличие, свойства/применение, доставка/оплата/возврат, реальные контакты, лицензии медиа и текст согласия. Если появятся требование мгновенного учёта остатков, варианты с общей ценой, обязательная онлайн-оплата или доступ контент-редактора без привилегий Studio — сначала пересмотреть соответствующую часть архитектуры, затем реализовывать.
