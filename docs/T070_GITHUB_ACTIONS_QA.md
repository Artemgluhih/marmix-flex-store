# T070 — GitHub-hosted read-only QA and signed-test gate

**Status:** T070 BLOCKED; T071 NOT STARTED. This document does not authorize live signed requests, temporary Admin membership changes, CSRF requests, fixture cleanup, or Production operations.

## Read-only CI delivered

`.github/workflows/t070-readonly-qa.yml` runs only for a push to `t070-preview-review` that changes the workflow or the listed T070 runner/tests. It has no `workflow_dispatch`, PR trigger, environment, secrets, artifact upload or mutation mode. The `GITHUB_TOKEN` permission is `contents: read`, checkout credentials are not persisted, and repository, branch, event SHA and remote HEAD must match before the runner starts. The job installs Node and pinned Playwright, installs Chromium on an Ubuntu GitHub-hosted runner, runs the existing signed-runner self-test and *only* `--dry-run`, then checks the local allowlisted JSON for five PASS verdicts, `liveSignedTestsExecuted=false` and `newFixturesCreatedByRunner=0`. The JSON is not uploaded. Failure/timeout does not become PASS. The pinned application Preview and Supabase Auth health CORS are checked by the existing dry-run; no fixtures or passwords are needed.

GitHub repository is public and Actions API was reachable. At preparation, the API listed zero workflows and one environment named `Preview` with **no** protection rules. The unauthenticated Actions-permissions and secrets metadata endpoints returned 401; these settings are **UNVERIFIED** rather than presumed safe. A workflow on this branch can run on `push`. GitHub requires a workflow file on the default branch to use `workflow_dispatch`; this review-only implementation intentionally does not change `main`. The first push of the workflow is the authorized read-only CI trigger. GitHub-hosted Ubuntu + Playwright Chromium installation follows the official Playwright CI approach; an actual CI step result is required before claiming Chromium PASS.

**First observed CI run:** GitHub Actions run `41812010208` on workflow commit `1570d7f67b7bbefde97bc5a9a63772a65d34a1ae` completed successfully. Checkout/branch/remote SHA checks, locked dependencies and pinned Playwright install, Chromium install, 50/50 self-tests with zero skips, and five dry-run checks all passed. The final guard independently read the local sanitized JSON and reported `signed execution false` and `fixtures created 0`. No report artifact was uploaded. This is a **CI read-only PASS**, not evidence of live signed Admin/RLS/CSRF behavior or current fixture SQL digests.

## Signed CI cannot safely execute under current boundaries

The current `--resume-final-p0` uses an ephemeral localhost Chromium sign-in, human prompts, and a frozen signed JWT kept in one process. It validates fresh 18-count/14-MD5 snapshots supplied by an independently trusted Preview SQL operator, not by the signed client. It has no CI credential adapter or direct trusted SQL channel. Copying a temporary password into a repository or log, adding privileged DB/service keys to the browser process, hardcoding snapshot CSVs, skipping separate approvals, or automatically running membership/CSRF mutations on `push` would weaken the tested boundary.

GitHub environment approval occurs **before a job starts**, not at each mutation inside a running job. The existing `Preview` environment has no required reviewer. Splitting active/CSRF/revoked work into separately approved jobs would destroy the single in-memory frozen JWT; passing it via output, artifact, cache or secret would violate the approved design. An automatic `push` live workflow would also turn every later review-branch push into a potential mutation trigger. `workflow_dispatch` for a review-only workflow is unavailable without a default-branch workflow. Therefore **live signed CI is BLOCKED**, and no live workflow, secrets or fixture manifest were added.

Before a future live implementation, Owner must decide whether to authorize a minimal default-branch dispatch entry and protected GitHub environment(s), or choose a different supported trusted approval channel. Security review must then specify a single-process credential lifecycle, exact project/Preview SHA and fixture manifest guards, a separately protected trusted SQL/membership operator with least privilege, verified action-time approvals for activation, wrong-Origin, missing-Origin and revocation, independent 18 counts/14 MD5 and REAL 10/10 before/after each phase, an explicit JWT expiry budget, and an emergency exact-UUID revoke procedure. Protect secrets at environment scope and restrict use to the review branch; the Owner must enter the temporary credential via GitHub's secret UI, never chat/CLI arguments/Git. Pin every third-party action by commit, disable traces/HAR/screenshots/storageState/artifact upload, sanitize errors and reports, and fail closed on unknown results without retry. Neither a secret existing nor an environment approval by itself authorizes a live mutation.

The one retained temporary Auth user/membership and TEST_ONLY product, WebP/image and order remain unchanged by this CI work. Historical signed SELECT/UPDATE and Storage upload/delete evidence must never be repeated by a future continuation. Natural expiry/refresh and successful Admin Product Create remain separate explicit acceptance decisions. The precise fixture cleanup order and safeguards remain in `T070_QA_REVIEW.md`; cleanup requires its own action-time approvals.
