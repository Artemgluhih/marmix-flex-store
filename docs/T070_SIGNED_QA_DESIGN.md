## Existing boundaries and acceptance

T070 is P0. The plan calls for login → catalog/media → orders, direct denials, a full Admin E2E and RLS/CSRF matrix, including session expiry, Storage and revoked Admin. The completed LIVE Owner/Admin, Category, TEST_ONLY Product Editor/Media and synthetic Orders UI checks and the TRANSACTIONAL SQL checks remain valid in their stated scope. The anonymous browser audit covered 16 fetched chunks and anonymous Admin HTTP only. The remaining signed-session checks cannot be inferred from those results.

The app uses request-scoped cookie Supabase Auth and getUser, then an active own admin_users membership check. requireAdminMutation checks the exact Origin/Host/protocol before the user/membership check; it rejects missing Origin. The proxy refreshes the app session and adds private/no-store headers, but membership authorization is in the Admin guard and policies. The product edit action uses the guarded Server Action, an explicit field allowlist and an authenticated user client. Storage INSERT/SELECT/DELETE policies require active membership and a bounded product path; no UPDATE policy permits upsert. The product-create invoker RPC inserts catalog_kind REAL. These are source-code findings, not live signed-token outcomes.

## Local runner architecture and credential isolation

Use a **new, dedicated Owner-operated Windows Playwright Chromium program**, separate from the existing anonymous read-only runner. A single process orchestrates an isolated, nonpersistent headful browser context and cookie-isolated direct API requests. It must not use a persistent browser profile, Playwright storageState export/import, HAR, trace, video, screenshot, download, console-body capture, debug protocol log or automatic failure artifact. No test runner retries for mutations.

The Owner enters disposable synthetic test credentials directly into a minimal ephemeral localhost page in that browser. Bind its listener only to 127.0.0.1 on a random port, with no remote access, no external scripts, strict CSP (only the exact Supabase Preview Auth origin for connect), no request-body logging, autocomplete off and no local persistence. Its in-memory code sends credentials directly to the exact Preview Auth password endpoint using the **publishable** key. It immediately clears the password field and reference. It must never POST credentials to the local HTTP listener or to the deployed app. The browser/Node boundary transfers only the short-lived access token in Playwright process memory, not through a URL, file, argument, environment variable, console or report. A dry-run without credentials must verify the exact Auth origin, network policy and CORS before the Owner enters anything; failure aborts sign-in. The refresh token, if returned by Auth, must never be saved or handed to the direct-probe client. Do not use a Supabase SDK configuration that persists or automatically refreshes the probe session.

For application-cookie checks the Owner may sign into the **existing Preview Admin UI** in a separate disposable context after temporary membership activation. The runner does not extract cookie values, call storageState or share that browser cookie jar with raw PostgREST/Storage probes. The dedicated direct-probe API context sets the bearer and publishable key only in memory, accepts only the exact Preview Supabase HTTPS origin and redirects disabled, and is disposed after use. The application context is closed before process exit. On Windows, Chromium and the OS may still create transient process/profile or paging artifacts; the design promises **no application-generated persistent credential artifact**, not a proof that an operating system never pages memory. If that stricter physical-RAM guarantee is required, this approach is BLOCKED pending a separately approved hardened environment.

The runner writes only an allowlisted local verdict file (phase, status code, affected-row count, permitted cache/robots directives, unchanged-state booleans, elapsed time and UNVERIFIED reason). It never writes credentials, bearer, refresh token, cookies, Authorization or Set-Cookie values, request/response bodies, real contact data, private IDs or session hashes. Fixture UUIDs/Storage paths remain volatile in the run and can be supplied separately to the trusted cleanup operator if an incident occurs; do not include them in the public QA report. Generic error handlers must suppress exception objects because libraries may include request headers. Use a strict schema for output and no test framework attachment.

**Production isolation:** hardcode and compare the exact Preview project reference and exact READY deployment origin after an Owner-provided confirmation of current SHA. Reject custom URL, redirects, alternate ports, credentials in URL, project mismatch, Vercel Production host or unapproved branch. Check the project via read-only trusted Preview channel before provisioning. The runner's request dispatcher must accept only enumerated paths, methods and exact fixture IDs/paths, with no free-form target URLs. A failed guard stops before credential entry or writes. Never use service_role/Secret for ordinary direct probes or Admin CRUD; trusted Preview provisioning/cleanup is a separate, explicitly approved phase.

### Threat → control → fail-closed result

| Threat | Technical prevention | Fail-closed behavior |
|---|---|---|
| Password disclosure | Owner types disposable credentials in isolated local browser page; no arguments, env file, chat, URL, local POST, logging or screenshot. | Abort if listener binds beyond loopback, CSP/CORS check fails, external resource loads or credential field cannot be cleared. |
| JWT/refresh disclosure | Bearer only in volatile probe memory; refresh token discarded; no storageState, cookies export, trace or body/header logs. | Destroy contexts and mark UNVERIFIED on any unexpected token-bearing output path. |
| Disk session persistence | Nonpersistent context, no profile path or save-state API; ephemeral listener; no artifact capture. | Abort if a proposed library/config needs a persistent profile. OS swap/crash-dump behavior remains an explicit environmental limit. |
| Console, HAR, trace, screenshot PII | Disabled by construction; whitelist numerical/redacted output; suppress raw errors. | Discard output and stop if a raw header/body/secret would enter a report or log. |
| Production request | Exact Preview web and Supabase project/origin allowlists, manual redirects, project/SHA preflight. | Reject before sign-in or mutation if any origin/project/branch differs. |
| JWT refresh during revocation | Freeze original bearer and expiry in memory; no SDK refresh, separate cookie session. | If original token expires or changes, revoked-with-valid-token = UNVERIFIED; never substitute a new token. |
| REAL data edit | Only approved present TEST_ONLY UUID/object and synthetic order; conditional predicates, field allowlists and before/after full-row digests. | Stop immediately on unexpected affected row or digest change; preserve exact incident IDs for Owner cleanup. |
| Mutation retry after timeout | One attempt per exact operation; no automatic retries/redirects. | Treat timeout as unknown, independently inspect exact target first; do not blindly repeat. |
| Incomplete fixture cleanup | Exact-ID/path conditional cleanup, independent residual counts and identical canonical REAL digest SQL. | STOP, preserve exact identifiers privately, no broad deletion; request Owner guidance. |
| Misleading denial | Record status **and** affected rows/object persistence; distinguish policy denial from missing target. | A 2xx/204 with zero rows is only PASS if present target and independent unchanged state are proven; unexpected success is FAIL. |

## Signed Auth/RLS execution matrix (future approval required)

Every phase begins with a live read-only baseline and present exact fixtures. Capture the signed user UUID, access-token expiry and exact fixture identifiers in memory; do not publish them. A SQL SET LOCAL ROLE simulation is TRANSACTIONAL evidence only, never signed-JWT evidence.

| Phase | Request and target | Required proof |
|---|---|---|
| Non-admin | Fresh signed Auth user **without** membership. Auth user endpoint confirms identity; app Admin route denial is separate from direct API. SELECT exact unpublished TEST_ONLY product and exact private synthetic order; attempt UPDATE of one allowlisted TEST_ONLY product field with Prefer return=representation; attempt Storage upload at a single absent bounded key and delete of the existing isolated WebP. | RLS hides private rows; UPDATE returns no changed representation/affected row (HTTP may be 204); independent trusted SELECT proves exact product full-row digest unchanged. Upload object absent; delete target still exists and metadata unchanged, regardless of API success wording. No REAL rows touched. |
| Active temporary Admin | Trusted Preview channel adds **one** is_active=true membership for same disposable UUID. Verify own membership and signed Auth identity. Direct read-only SELECT of exact TEST_ONLY product/order and Storage metadata through the *user bearer*. Separately use normal Admin UI cookie context for route read-only checks. | Present rows visible only to active Admin. No ordinary CRUD through privileged channel. This phase can establish positive visibility without adding another mutation. |
| Revoked Admin | Trusted channel changes only this membership is_active=false. Keep the **identical original access token**, verify exp is still in future with a safety margin and Auth user endpoint succeeds for that bearer; no refresh. Immediately repeat private SELECT, conditional TEST_ONLY UPDATE and bounded Storage upload/delete denials, then normal app route denial in its cookie context. | Same-token validity and membership revocation independently observed; zero changed rows/objects by trusted exact reads and hashes. The app cookie may carry a different token and its route result is reported separately, never as same-bearer proof. If validity cannot be independently confirmed, label valid-token revocation UNVERIFIED. |

Direct PostgREST requests must use the publishable key and signed user bearer against the exact Preview project; no service_role, SQL role impersonation or assumed admin API. An existing target is essential. Do not count HTTP 200/204 with zero affected rows as a successful write, or a nonexistent UUID denial as an RLS test. Storage delete may return no error despite no deletion, so exact object persistence decides the verdict. If a denied probe unexpectedly mutates a fixture, stop further probes, preserve evidence without secrets and escalate as a confirmed vulnerability; do not normalize it away with cleanup.

## Server Action / CSRF negative design

Use the actual rendered TEST_ONLY product edit form in a valid temporary Admin cookie context. Its bound product ID, action reference and form encoding must come from that **same deployed page/session**, never an invented Server Action identifier or a copied old build. Choose one approved edit field/value and record exact TEST_ONLY product full-row digest before each attempt. Construct two single-use requests through the same cookie-jar request context: (1) deliberately wrong Origin; (2) omitted Origin. Preserve the actual Host/HTTPS context. Do not disable application or framework defenses. The app guard rejects both; Next.js also enforces an Origin/Host check, but the response layer that rejects first must be reported as observed rather than guessed.

A standard browser fetch cannot reliably omit or forge Origin; the request context must be tested to establish its **actual sent** Origin presence/absence without logging cookies or values. If the framework action payload cannot be obtained safely from the real form, or the request client injects Origin unexpectedly, mark the live CSRF case UNVERIFIED and stop. No probing random action IDs. A redirect or HTTP error alone is insufficient: independently reread the exact TEST_ONLY row and compare the same digest after each attempt. Unexpected 2xx plus changed row is FAIL and halts the run. This is a mutation probe and needs separate Owner approval, even though denial is expected.

## Authenticated HTTP privacy and traffic design

With a temporary signed active Admin browser context, observe real deployed GET responses for /admin/orders and the exact TEST_ONLY product editor. Record only status, Cache-Control directives, presence/value of X-Robots-Tag if any, robots metadata boolean/directives and whether the response is publicly cacheable. Never store HTML, RSC payload, Set-Cookie, cookie jar or response body. Compare with a separate anonymous context: protected route redirect/login, no synthetic private marker. The previous anonymous HTTP PASS does not prove authenticated headers.

For traffic-level PII, use only one synthetic order with distinctive non-personal markers; scan designated anonymous HTML/RSC/JSON and direct API responses in memory for those markers and record booleans/counts, not content. In the authenticated context private synthetic data is expected; verify only that it appears in the authorized view and is absent from anonymous traffic. Capturing all loaded chunks or all traffic is a larger audit and cannot be claimed from this limited marker check. Do not inspect or persist REAL order contacts. If the app returns private cacheable responses, or synthetic markers leak anonymously, stop and classify as vulnerability. No real order submission endpoint is invoked.

## Expiry, refresh and revocation are distinct

1. **Natural expiry:** retain a raw access token without refresh, wait until its real exp plus clock-skew margin, then observe Auth/PostgREST rejection. Do not change Auth settings or system clock.
2. **Refresh:** a separate normal app cookie session may refresh through the request proxy; prove a new valid session and continued authorization without recording old/new token values. Merely reloading before expiry is session persistence, not refresh proof.
3. **Expired token denial:** direct request with the same expired raw token fails; report it separately from membership revocation.
4. **Valid-token membership revocation:** before expiry, use the same raw bearer from active Admin phase after changing only temporary membership; Auth user endpoint still accepts it while DB/Storage deny private access. Logout revokes refresh tokens but access tokens may remain valid until exp; logout alone does not demonstrate revoked membership enforcement.

If real expiry is too long for one supervised run, keep the process/context alive without writing a checkpoint token, or stop and mark the natural-expiry case UNVERIFIED. A later run signs in anew and cannot be passed off as an observation of the prior token. Owner must explicitly decide whether to wait in a separate supervised run or accept a documented T070 exception. Session timeout or network loss is not proof of expiry.

## Admin Product Create: unresolved acceptance choice

**A — deliberate Preview-only TEST_ONLY create path.** A separately designed, approved change would make the *normal Admin Create workflow* produce a forced unpublished, unfeatured TEST_ONLY row with bounded SKU/slug in the exact review branch and Preview project. The existing invoker RPC currently hardcodes REAL, so this cannot be achieved merely by changing the UI or supplying an extra form field. It likely needs a reviewed application/RPC contract and Preview-only database migration or equivalent isolated transaction boundary, active user RLS and a fail-closed production exclusion. It must not enable TEST_ONLY creation or cleanup in Production. Risks: additional app/DB attack surface, deployment/configuration leakage, new cleanup semantics and a departure from approved architecture. This is **not authorized** here and needs explicit architecture/DB/Owner approval and rollback plan before code.

**B — explicit Owner acceptance exception.** Keep Admin Create unchanged and do not create REAL data for QA. Existing LIVE TEST_ONLY edit/media, Category and Orders flows plus source/synthetic validation of create/RPC cover adjacent behavior, but the signed Admin Create form → RPC → REAL row transaction and its UI error/retry path remain **UNVERIFIED**. This is a literal gap against “full Admin E2E”; T070 cannot be silently declared complete. Owner must explicitly accept the bounded exception and residual risk, or choose A. No SQL rollback of an independent browser action is offered as a substitute.

## Minimal fixture lifecycle for a separately approved run

Provision one resource at a time only after exact Preview project/branch and zero-collision checks. Generate UUIDs once in trusted Preview provisioning, retain exact IDs/paths in volatile incident worksheet controlled by Owner; do not commit or print them in general reports. Record REAL counts, identity sets and full-row digests before and after with the **same canonical SQL, stable ID order and serialization**, including products, categories, memberships, product images and Storage. Separate trusted fixture setup/cleanup from signed user/RLS evidence.

| Fixture | Need, scope and provisioning | Side effect / exact cleanup / independent proof |
|---|---|---|
| One disposable Auth user | Synthetic non-real address; trusted Preview Auth provisioning; no real email notification. Signed non-admin → active → revoked. | Auth audit logs may remain. Sign out/revoke session, delete only its exact temporary membership, then exact Auth user/identities by UUID. Independent counts: one original user, one active Owner membership, temporary UUID/identity/membership absent. On failure STOP; never touch Owner membership. |
| One temporary membership | Same disposable user UUID, active then inactive; trusted Preview channel, no new role. | Exact UUID delete after probes. Independently prove own membership absent and Owner active count one. Never deactivate Owner. |
| One unpublished TEST_ONLY product | Present RLS UPDATE/CSRF target; trusted Preview fixture provisioning only, no normal Create action (it makes REAL). No REAL memberships, no price/availability claim, no public exposure. | After child media cleanup, conditional exact UUID delete. Verify UUID/SKU/slug absent, REAL digests unchanged. Stop on unexpected association or publication. |
| One synthetic WebP | Necessary for meaningful Storage delete denial and optional media boundary; only under exact TEST_ONLY product prefix, one generated key, upsert=false. Public bucket means temporary public URL, so nonconfidential image only. | Remove only exact image row and exact Storage path via approved boundary; verify folder has no orphan, original three image/Storage identities/digests unchanged. No broad-prefix delete. |
| One synthetic order | Needed for private SELECT and traffic marker; one non-real contact set and one synthetic snapshot. Trusted Preview SQL fixture channel; **never** /api/order-requests, thus no app Telegram path. | Check DB triggers/hooks and notification risk before insert; exact UUID/idempotency cleanup with immutable digest guard after probes; independent orders zero and REAL digests equal. If notification risk is not excluded, omit fixture and mark dependent traffic PII scenario BLOCKED. |

A partial failure pauses tests. Preserve exact IDs in a private, ephemeral Owner-controlled recovery handoff (never a public QA file), inspect current state read-only, request action-specific cleanup guidance; no broad delete, no silent retries and no service_role for ordinary Admin CRUD. Provisioning and exact cleanup may use the separately approved trusted Preview channel; ordinary admin and direct denial tests must use signed user Auth/RLS. Approval must cover each persistent fixture, denied mutation probe, trusted active/revoked membership change, exact cleanup, and any temporary credential capture mechanism before execution.

## Decision and evidence limits

**Security design verdict: PASS as an architecture for a future, separately approved implementation; execution remains BLOCKED.** The approval must review the concrete runner code and credential/CORS dry-run before any account or fixture is created. No tool can prove that Windows never pages RAM; if the Owner requires that absolute guarantee, this design is BLOCKED and a hardened environment is required.

**Remaining mandatory P0 evidence:** signed non-admin present-target PostgREST/Storage denial; same valid bearer after revocation with direct DB/Storage and route denial; live wrong/missing-Origin Server Action refusal with unchanged present target; authenticated Admin privacy/cache responses; synthetic-marker traffic isolation; natural expiry/refresh unless Owner explicitly accepts a specific exception; and Product Create decision A or B. The Product Create full signed create path is still a literal acceptance gap under B. Full all-chunk scanning and broader client permutations are P1 residual audit scope, not asserted PASS. No confirmed vulnerability follows from the completed checks; unverified paths are not cleared.

**Owner actions/approvals needed:** choose A or B for Product Create; approve a reviewed dedicated local runner and credential entry after code/security review; approve one temporary Preview Auth user/membership, exact TEST_ONLY product/WebP/order as needed, negative writes and trusted cleanup; arrange active/revoked membership timing and supervised natural-expiry run or explicit exception.
